# 第一阶段实战：企业客服工单分诊助手

## 一、为什么选择这个项目

客服工单分诊具有真实企业场景的典型特征：输入是非结构化文本、分类规则复杂、人工处理重复、错误成本不对称，同时输出容易标注和评测。它适合用于学习 LLM 的能力边界，又不需要在第一阶段引入 RAG 或复杂 Agent。

这个项目不是做一个聊天页面，而是完成一个可验证的业务闭环。

## 二、业务背景

假设一家 SaaS 企业每天收到大量客户工单，当前由人工完成：

1. 阅读工单。
2. 生成一句话摘要。
3. 判断业务分类。
4. 判断紧急程度。
5. 分配到对应团队。
6. 识别退款、数据泄露、安全攻击等风险。

当前基线需要通过访谈或假设明确记录，例如：

| 指标 | 示例基线，需替换为自己的设定 |
|---|---:|
| 日工单量 | 2,000 |
| 人工平均分诊时间 | 90 秒/单 |
| 分错团队比例 | 8% |
| 高优先级漏判率 | 5% |
| 每次错误转派额外耗时 | 15 分钟 |

## 三、项目范围

### 本阶段要做

- 工单摘要。
- 一级、二级分类。
- 优先级判断。
- 责任团队推荐。
- 风险标签。
- 无法确定时转人工。
- 结构化输出、校验、有限重试和降级。
- 离线评测、成本和延迟统计。

### 本阶段不做

- 自动回复客户。
- 查询企业知识库。
- 自动退款、封禁账号等不可逆动作。
- 自主多步骤 Agent。
- 微调模型。

明确不做什么，是企业项目范围控制的一部分。

## 四、输出契约

参考结构：

```json
{
  "summary": "客户生产环境无法登录，已持续约30分钟",
  "category": "account",
  "subcategory": "login_failure",
  "priority": "P1",
  "target_team": "identity_platform",
  "risk_tags": ["production_outage"],
  "needs_human_review": true,
  "reason_codes": ["MULTIPLE_USERS_AFFECTED", "PRODUCTION_BLOCKED"]
}
```

生产注意事项：

- 所有枚举由业务代码定义，模型不能自由创造类别。
- 不直接信任模型输出；必须进行 Schema 和跨字段业务校验。
- 不把模型自报的 `confidence` 当作校准概率。
- `reason_codes` 应映射到可审计的业务规则，而不是只保存自然语言理由。
- 原始工单可能包含恶意指令，必须始终当作数据处理。

## 五、数据集设计

最低要求 50 条，建议 100～200 条。可以使用脱敏历史数据；没有企业数据时，先人工设计种子案例，再用模型扩展，最后逐条审核。

数据至少覆盖：

- 常见正常案例。
- 模糊、信息不足和多意图案例。
- 高优先级少数案例。
- 拼写错误、中英文混合、口语和情绪化表达。
- 类别相近的困难案例。
- Prompt Injection、伪造内部指令和超长文本。
- PII、密钥或商业敏感信息。

推荐字段：

```json
{
  "id": "T-001",
  "input": "工单原文",
  "expected": {
    "category": "account",
    "priority": "P1",
    "target_team": "identity_platform",
    "needs_human_review": true
  },
  "tags": ["high_priority", "ambiguous"],
  "source": "handcrafted",
  "reviewer": "name-or-role",
  "dataset_version": "v1"
}
```

将数据拆为开发集和测试集。Prompt 调试只能看开发集；最终结果在冻结的测试集上运行。

## 六、必须实现的三条基线

### 基线 A：关键词或规则

用于证明 LLM 相比传统方案是否真的增加价值。至少覆盖高优先级和安全风险规则。

### 基线 B：纯 LLM

统一 Prompt、固定 Schema，模型直接完成全部判断。

### 基线 C：混合方案

高风险硬规则 + LLM 语义分类 + 业务代码校验 + 人工兜底。

企业项目通常不是“规则和 AI 二选一”，混合方案往往更容易控制风险。

## 七、评测指标

| 指标 | 含义 | 建议关注点 |
|---|---|---|
| Schema 通过率 | 输出能否被系统解析 | 重试前、重试后分别统计 |
| Category Macro-F1 | 各类别是否都能正确识别 | 防止大类掩盖小类 |
| P1 Recall | 高优先级是否漏判 | 通常比总体准确率更重要 |
| Human-review Recall | 困难案例能否被交给人工 | 衡量安全退出能力 |
| 错误转派率 | 是否发送给错误团队 | 可映射实际额外成本 |
| P50 / P95 延迟 | 用户和批处理体验 | 不能只看平均值 |
| 单工单成本 | 模型和基础设施费用 | 推导月度成本 |
| 自动化率 | 无需人工处理的比例 | 必须和风险指标一起看 |

第一版验收门槛可设为：

- Schema 重试后通过率 ≥ 99%。
- P1 Recall ≥ 95%。
- Category Macro-F1 ≥ 0.85。
- 对注入案例不执行输入中的指令。
- 无法确定时能够转人工，而不是强行分类。

门槛只是练习起点，真实企业应由业务风险和历史基线决定。

## 八、生产架构

```text
工单系统
   ↓
输入校验 / 脱敏 / 长度限制
   ↓
Prompt 组装器（版本化）
   ↓
模型网关（超时、限流、重试、熔断）
   ↓
Schema 校验 + 业务规则校验
   ↓
低风险自动路由 ─────→ 人工复核队列
   ↓                         ↓
工单系统更新 ←────── 审核结果与反馈
   ↓
指标、审计日志、回归数据集
```

## 九、工程要求

- Prompt、模型、Schema 和数据集都有版本号。
- 请求有 Trace ID，重试具有幂等性。
- 配置超时、并发限制、最大重试次数和回退模型。
- 日志不记录未脱敏的客户敏感信息。
- 模型返回值只作为候选决策，由业务代码执行路由。
- 高风险和低置信场景进入人工队列。
- 保存人工修正结果，用于错误分析和后续数据闭环。

## 十、实验报告结构

1. 业务背景和当前基线。
2. 为什么选择或不选择 LLM。
3. 数据集构造与局限。
4. 三条基线方案。
5. 评测指标和验收门槛。
6. 结果表格与错误案例。
7. 成本、延迟与容量估算。
8. 安全、隐私和降级方案。
9. Go / No-Go 上线建议。
10. 下一阶段如何用 RAG、微调或 Agent 改进。

## 十一、答辩问题

- 为什么不用普通分类模型或规则引擎？
- 为什么 P1 Recall 比总体 Accuracy 更重要？
- 模型返回合法 JSON，但团队分配错误，系统在哪一层发现？
- API 故障时业务是否还能运行？
- Prompt 更新如何避免线上回归？
- 如何估算节省的人力和错误转派成本？
- 哪些动作永远不应由当前版本自动执行？
