# 第一阶段可执行学习单

这份学习单解决“看完资料以后不知道做什么”的问题。第一阶段分成四个单元，每个单元都有指定资料范围、练习输入、提交物、参考答案和验收标准。

不要先看答案。推荐顺序：

```text
带着问题看指定资料 → 完成最小任务 → 自己写结论 → 对照答案 → 修改并复盘
```

## 单元一：判断一个场景是否值得使用 LLM

时间：2～3 小时

### 带着三个问题学习

1. 模型、应用编排、业务系统、评测治理分别负责什么？
2. LLM 相比规则和搜索，多提供了什么能力，又失去了什么确定性？
3. 什么场景同时满足高频、可评测、失败可接管？

### 指定中文资料

1. [阿里云百炼：什么是模型服务平台百炼](https://help.aliyun.com/zh/model-studio/what-is-model-studio)：只看产品定位、模型服务和应用开发能力。
2. [Datawhale 第一章：大模型简介](https://datawhalechina.github.io/llm-universe/#/C1/C1)：只看 1.1 LLM 简介和 1.4 大模型开发整体流程。

### 练习

从自己熟悉的业务中选 3 个场景，分别按 1～5 分评价：业务频率、人工耗时、语言复杂度、数据可得性、输出可验证性。错误成本不计入总分，而是单独作为否决条件。

提交物：一张场景评分表和一张四层生产架构图。

### 参考答案

示例判断：客服工单分诊通常适合作为第一个项目，因为输入是非结构化文本、结果可人工标注、错误可被复核、可以先以建议模式上线。自动退款不适合作为第一阶段项目，因为动作不可逆且需要鉴权、金额限制、幂等和审批。

四层图至少包含：模型能力层、Prompt/Workflow 应用层、工单与业务 API 层、横切的评测/权限/日志/人工兜底。

### 验收标准

- 不以“模型能回答”作为选型依据。
- 至少写出一个明确不使用 AI 的反例。
- 能说明为什么首版只做建议或分诊，不做自动退款。

## 单元二：验证模型的概率性和 Prompt 契约

时间：4～5 小时

### 带着四个问题学习

1. Temperature 降到 0 后是否绝对稳定？
2. Few-shot 和结构化 Prompt 分别在解决什么问题？
3. JSON Schema 能保证结构、语义还是业务正确？
4. Prompt 为什么也需要版本和回归测试？

### 指定中文资料

1. [Datawhale 第二章：基本概念](https://datawhalechina.github.io/llm-universe/#/C2/1.%20基本概念)：只看模型调用中的消息、Token 和生成参数。
2. [Datawhale：Prompt Engineering](https://datawhalechina.github.io/llm-universe/#/C2/3.%20Prompt%20Engineering)：学习清晰具体、给模型思考时间和迭代原则。
3. [书生浦语：提示词工程实践中文视频](https://www.bilibili.com/video/BV1tjS7YfEWJ/)与[中文任务文档](https://github.com/InternLM/Tutorial/tree/camp4/docs/L1/Prompt)：只学结构化提示词部分，不做小红书文案案例。

### 练习

1. 下载[20 条中文种子工单](../docs/downloads/stage-1/tickets-seed.jsonl)。
2. 任选 5 条，每条在 Temperature 0 和 0.7 下各运行 5 次。
3. 使用[实验记录模板](../docs/downloads/stage-1/experiment-record.csv)记录字段级一致率、Schema 通过率、P50/P95 和失败类型。
4. 分别编写零样本、带规则、带 2 个示例的三个 Prompt 版本，并保持测试数据不变。

提交物：三个 Prompt、实验 CSV、一页结论。自己完成后再对照[三个 Prompt 版本参考答案](../docs/downloads/stage-1/prompt-reference.md)。

### 参考答案

结果数值取决于模型，不存在固定准确率。合格结论应包括：低 Temperature 通常降低但不消除波动；示例可以改善格式和边界，但也可能产生示例偏置；Schema 只保证结构；Prompt 版本之间必须使用同一冻结测试集比较。

字段级稳定率可以定义为：20 次结果中，某字段的众数出现次数除以 20。不要只比较整段文本是否完全相同。

### 验收标准

- 记录模型名、模型版本、Prompt 版本、参数和测试集版本。
- 不能用 2～3 个成功样例得出“稳定可上线”。
- 至少保留一个反直觉失败案例。

## 单元三：建立结构、语义和业务三层校验

时间：4～6 小时

### 带着三个问题学习

1. Tool Calling 中是谁选择工具，谁真正执行动作？
2. 为什么合法 JSON 仍可能造成严重事故？
3. 哪些规则必须由确定性代码负责？

### 练习

1. 阅读[输出 Schema](lab/schema/ticket-triage.schema.json)，先自己实现结构校验。
2. 写跨字段规则：生产故障必须 P1 且转人工；安全事件必须进入安全团队；未知类别必须转人工。
3. 构造三条合法 JSON，但分别违反上述业务规则的测试。
4. 自己完成后，再查看[Go 参考校验器](lab/reference/validator.go)和[测试](lab/reference/validator_test.go)。

提交物：Schema、校验器、自动化测试和错误处理流程。

### 参考答案

正确分层是：JSON Schema 负责字段存在、类型、枚举和长度；业务校验器负责跨字段一致性；有副作用的工具调用还必须经过身份认证、授权、幂等和人工审批。模型只能提供候选结果，不能自己成为权限边界。

运行参考答案：

```bash
cd 01-llm-basics/lab
go test ./...
```

### 验收标准

- 测试中至少包含一个“Schema 通过但业务校验失败”的案例。
- 校验失败不会直接写入工单系统，而是有限修复或转人工。
- Prompt Injection 输入不能改变系统定义的优先级规则或调用真实工具。

## 单元四：用评测做 Go / No-Go 决策

时间：5～7 小时

### 带着四个问题学习

1. 为什么必须比较规则、纯 LLM 和混合方案？
2. 为什么高风险 Recall 可能比总体 Accuracy 更重要？
3. 自动化率提高是否一定更好？
4. 什么证据才足以进入小流量灰度？

### 指定中文资料

1. [Datawhale：如何评估 LLM 应用](https://datawhalechina.github.io/llm-universe/#/C5/1.如何评估%20LLM%20应用)：只学人工评估、简单自动评估和迭代闭环。
2. [第一阶段项目题](project-ticket-triage.md)：重点阅读三条基线、评测指标、生产架构和报告结构。

### 练习

1. 将 20 条种子数据扩充到至少 50 条，开发集和测试集分开。
2. 比较关键词规则、纯 LLM、规则 + LLM + 业务校验三条基线。
3. 统计 Macro-F1、P1 Recall、人工转交 Recall、Schema 通过率、P95 和单工单成本。
4. 填写 [Go / No-Go 报告模板](../docs/downloads/stage-1/go-no-go-template.md)。

### 参考答案

一个常见的合格结论不是“全自动上线”，而是 Conditional Go：只让混合方案处理低风险高一致性工单；P1、安全、退款、信息不足和注入案例全部转人工；灰度期间保留规则回退与一键关闭开关。

如果 P1 Recall 未达到门槛，即使总体准确率很高，也应 No-Go。真实实验数值必须来自你的模型和数据，不能照抄示例结果。

### 验收标准

- 同一测试集、Prompt 和统计口径下比较方案。
- 报告失败案例，不只展示平均指标。
- 上线范围、监控指标、人工兜底和回滚路径明确。
